# B1 · Keyboard focus must never land under the fixed ribbon (WCAG 2.4.11)

## 1. Problem
On Tonight, once the night ribbon is showing (fixed, top of the viewport), tabbing to glance rows and tickets can put the
focused element (partly) under the ribbon. Screenshot: `design/hardwood/audit/shots/B3-focus-under-ribbon.png`.

## 2. Repro
`/?sample=1&scene=live` at 400, 768, 1440 (height 900). Scroll so `[data-testid=tape]` is above the viewport (the
ribbon `.ribbon.on` appears; e.g. `window.scrollTo(0, tape.getBoundingClientRect().bottom + scrollY + 10)`), then
press Tab repeatedly. Focusables involved: `.gl__hit` (glance rows), toolbar buttons, `.ticket__hit`.

## 3. Root cause
- `public/static/css/base.css` line 2: `html{scroll-padding-top:64px}` — a fixed value; the ribbon is ~58px on desktop
  but taller when it wraps on phones (`.ribbon__in` has `flex-wrap:wrap`, `min-height:52px`), and when focus moves to
  an element that is already "visible" in the viewport but sits under the fixed ribbon, the browser does not scroll at all.
- `public/static/js/tonight/ribbon.js` `apply()` toggles `.ribbon.on` but tells the page nothing about its height.

## 4. Files owned
- `public/static/js/tonight/ribbon.js`
- `public/static/css/base.css` (only the `html{scroll-padding-top…}` rule)

## 5. Complete solution looks like
- In ribbon.js, when the ribbon turns on (and on resize while on), measure `ribbon.getBoundingClientRect().bottom` and
  set `document.documentElement.style.setProperty('scroll-padding-top', (bottom + 12) + 'px')`; when it turns off,
  `removeProperty('scroll-padding-top')` (CSS default 64px applies again).
- Add one `focusin` listener on `document` (registered in `mountRibbon`): if the ribbon is on and the focused element
  is not inside the ribbon/drawer, and `target.getBoundingClientRect().top < ribbonBottom + 12`, scroll the window up by
  the difference: `window.scrollBy({ top: rect.top - (ribbonBottom + 12), behavior: 'auto' })` (always instant; no smooth
  scroll, so reduced motion is respected). Ignore focus inside `.drawer`.
- Shift+Tab (moving up) gets the same treatment (focusin covers both).
- The ribbon stays `aria-hidden="true"` and non-focusable. No visual change to the ribbon.
- When the ribbon turns on while an element is focused, nothing jumps.

## 6. Out of scope
Ribbon content/layout; drawer focus trap; D1 header.

## 7. Acceptance tests (`tests/e2e/audit/B1.mjs`)
For w in 400, 768, 1440 (height 900), scene live:
- Scroll so the board is just above the viewport and assert `.ribbon.on` exists. Put focus on the first `.gl__hit`
  with `page.focus('.gl__hit')`, then press Tab 25 times (real keyboard). After each Tab, if `.ribbon.on` is present,
  assert `document.activeElement.getBoundingClientRect().top >= ribbon.getBoundingClientRect().bottom - 0.5`
  (skip the check when the active element is inside the ribbon or the drawer). Wait 50 ms after each key.
- Then press Shift+Tab 10 times with the same assertion.
- Audit "Accept when" — *Every Tab stop's rect top ≥ ribbon bottom.*
- No horizontal overflow; `page.errors` empty.
- Reduced motion run (`reducedMotion: true`) at 400: same assertions pass.
